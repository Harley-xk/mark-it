# AI 工作规则 —— 基础约定（最高优先级）

> 本文件是所有 AI 规则中优先级最高的基础约定。任何其他规则、历史代码风格或临时指令与本文件冲突时，**以本文件为准**。
> 适用范围：本仓库内所有由 AI 参与的开发工作（含文档撰写）。

## 0. 工程事实（所有规则的前提）

Mark It 是 **Electron + Vue 3 + TypeScript** 的桌面 Markdown 编辑器，**单包 npm 工程**（非 monorepo）：

| 项目     | 现状                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------- |
| 包管理器 | **npm**（`package-lock.json`，不使用 pnpm / yarn）                                                      |
| 构建     | `electron-vite`，产物输出到 `out/`，安装包到 `dist/`                                                    |
| 进程目录 | `src/main`（主进程）/ `src/preload`（预加载）/ `src/renderer`（渲染进程）/ `src/shared`（跨进程纯类型） |
| 校验命令 | `npm run lint`、`npm run typecheck`、`npm test`、`npm run build`                                        |
| 测试框架 | **Vitest**（纯函数单元测试）+ **Playwright**（Electron e2e），见 [testing.md](testing.md)               |
| git 钩子 | **未配置** lefthook / husky / commit-msg 钩子                                                           |
| 文档目录 | `docs/`（打包时已排除，见 `electron-builder.yml`）                                                      |

## 1. 文件头部注释（仅限新增代码文件）

**只有新增的业务源代码需要署名**；已有文件**不强制回补**（改动存量文件时保持原样，不必为了补注释而制造额外 diff）。配置文件、测试文件、资源文件**不需要**携带头部注释。

需要署名的文件（新增时）：

- `.ts` / `.js` / `.mjs` / `.cjs` / `.vue` 等业务源码（页面、组件、路由、状态、服务、工具等模块）

不需要署名的文件：

- **配置文件**：`.json` / `.yaml` / `.yml` / `.env*` / `.gitignore` / `*.config.*` / `tsconfig*` 等
- **测试文件**：`*.spec.ts` / `*.test.ts` / `test/**` / `e2e/**` 等各类测试
- **资源文件**：样式（`.css` 等）、图片、字体、HTML 入口、类型声明（`*.d.ts`）等
- **构建脚本**：`scripts/**` 下的一次性构建 / 发布脚本

新增的代码文件，必须在文件首行携带如下格式的头部注释：

```ts
/*
 * 作者: Harley-xk
 * 创建: 2026-11-04
 *
 * 描述: 当前文件的描述
 */
```

字段说明：

| 字段 | 说明                                                       |
| ---- | ---------------------------------------------------------- |
| 作者 | 统一填写项目维护者标识 `Harley-xk`（与 GitHub 仓库归一致） |
| 创建 | 文件创建日期，格式 `YYYY-MM-DD`                            |
| 描述 | 用一句话（中文）概括当前文件的职责或用途                   |

## 2. 注释语法按语言适配

头部注释的语法必须与文件实际使用的语言匹配：

| 文件类型                        | 注释语法                                                   |
| ------------------------------- | ---------------------------------------------------------- |
| `.ts` / `.js` / `.mjs` / `.cjs` | `/* ... */` 块注释，置于文件首行                           |
| `.vue` / `.html`                | `<!-- ... -->`，置于文件首行（位于 `<script setup>` 之前） |
| `.json`                         | JSON 标准不支持注释，跳过头部注释                          |
| `.md`                           | 文档文件，不强制携带头部注释                               |

## 4. 文档先行

**所有业务改动都必须文档先行**：先更新 `docs/`，再实际写代码。不存在「改动小就不必写」的例外。

1. **适用范围**：新增功能、功能变更、交互调整，以及会改变既有行为的缺陷修复，一律适用。新的独立能力在 `docs/` 新增设计文档（需求背景、方案设计、接口约定、数据模型等）；对已有功能的改动更新对应功能文档，不重复造文档。涉及架构调整、数据结构变更、IPC 契约变更、持久化格式变更或跨模块交互设计的，必须单独成文或重写对应章节，不能只在功能文档里补一句
2. 文档统一放在 `docs/` 目录下，按主题归入子目录（划分见 `docs/README.md` 第 1 节），根目录只保留索引；**新增文档使用中文文件名**（存量 `docs/更新与发布/github-release.md` 保持原名，不回改）
3. `docs/` 已从安装包中排除，可以放心存放设计与发版文档
4. 代码实现与文档保持同步：实现偏离设计时，先更新文档再改代码
5. 文档中的图表（架构图 / 流程图 / 时序图 / 状态机 / 实体关系图等）**一律使用 Mermaid 代码块（` ```mermaid `）绘制，禁止使用 ASCII 字符画**；公式、规则表、命令输出等非图形内容不在此限
6. **内置用户手册与更新说明**：两者采用**一致的判定口径**——都以「是否对用户有价值」确定是否更新，不局限于可见的界面变化；但内容按各自场景独立撰写，**不要求互相复制或一一对应**。

   - **内置用户手册** [`src/renderer/src/assets/welcome.md`](../src/renderer/src/assets/welcome.md)（工具栏「使用手册」打开的内容，也是首次启动的欢迎页）：改动涉及用户的操作方式、行为结果、注意事项或使用体验时，必须更新，并在交付说明中写明改了哪些条目；
   - **发版更新说明**：面向当次发布，按「是否对用户有价值」筛选并合并同类项，技术实现细节一律不写（撰写规则见 [docs/更新与发布/github-release.md](../docs/更新与发布/github-release.md) 第 3.1 节）；
   - 纯内部重构、对用户没有可感知价值的，两者都可不改，但需在交付说明中说明理由；
   - 这个判据只决定手册与更新说明，**不是**判断是否需要写文档的依据

## 5. 完成定义（DoD）

任何代码改动（含 AI 生成）视为「完成」，必须同时满足：

1. `npm run lint` 通过（ESLint，含 Prettier 一致性检查）
2. `npm run typecheck` 通过（主进程 + 渲染进程双 tsconfig）
3. `npm test` 通过（Vitest 纯函数回归；改动 `src/renderer/src/utils/**` 中带分支 / 边界的纯逻辑时，按 [testing.md](testing.md) 的风险驱动原则补 / 改用例，不逐文件配 spec）
4. 涉及 `electron.vite.config.ts`、`electron-builder.yml`、`.github/workflows/**` 的改动，额外执行 `npm run build`（或对应平台的 `build:*`）
5. 涉及主进程 / 窗口管理 / IPC / 文件读写 / 自动更新 的改动，必须用 `npm run dev` 实际启动验证，并在交付说明中写清验证方式
6. 已按「文档先行」更新 `docs/`（所有业务改动）；实现偏离设计的，已先改文档再改代码
7. 改动对用户有可感知价值（操作方式、行为结果、注意事项、使用体验等）的，已更新内置用户手册 `src/renderer/src/assets/welcome.md`（见第 4 节第 6 条），并在交付说明中写明；纯内部重构且对用户无价值的可不改
8. 仓库当前**没有 pre-commit 钩子**，上述命令需在提交前由执行者自行运行，不得假设钩子会兜底

## 6. 提交信息规范

沿用仓库既有的 **Conventional Commits** 风格，提交信息统一使用固定格式：

```text
<type>(<scope>): 内容概述
```

| 字段     | 约定                                                                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| type     | `feat` / `fix` / `refactor` / `perf` / `style` / `docs` / `chore` / `build` / `ci` / `revert`                                                                 |
| scope    | 改动所属模块，小写：`file` / `preview` / `editor` / `toolbar` / `tabs` / `outline` / `update` / `export` / `session` / `build` / `ci` / `docs` / `release` 等 |
| 内容概述 | 一句话说明本次改动要点，**使用中文**                                                                                                                          |

示例：

```text
feat(file): 文件变更被动刷新，保存时检测冲突并展示差异
fix(preview): 预览链接交由系统打开，修复外部链接导致窗口卡死
chore(release): 发布 1.4.1
```

合并、还原等自动生成的提交不受此限制。
